新火焰图已经把问题说得很清楚：**时间几乎全花在 `WebGLRenderer.render` → `renderScene` → `renderBufferDirect` 上**。下面分「这句话什么意思」和「怎么优化」两部分说。

---

## 1. 这代表什么（为什么也算「执行脚本」）

在 Performance 里，**「执行脚本」不只包含你自己的 `update` 逻辑**，也包括 **Three.js 在 CPU 上为每一帧准备并调用 WebGL API** 的时间（`renderBufferDirect` 就是在对某个几何体发绘制指令）。

所以：**瓶颈是「CPU 侧渲染提交」——典型表现是 draw call 多、材质/程序种类多、阴影与透明物体多等**，而不是你上一张图里那种纯游戏逻辑。

火焰图里两次 `renderBufferDirect`（约 4.8ms + 7.5ms）往往对应 **两类材质/程序**（例如一批不透明物体 + 一批透明/叠加，或阴影 pass 里的批次），需要减少「要单独画一遍」的对象数量。

---

## 2. 优化方向（按收益/难度大致排序）

### A. 减少 draw call（最对症）

- **实例化（`InstancedMesh`）**：草地、重复道路、相同几何只换矩阵的物体，用实例画一批，而不是 17×17 个独立 `Mesh`。
- **合并几何**：静态区块用 `BufferGeometryUtils.mergeGeometries`（或按地块分块合并），把很多小 mesh 合成少量大 mesh。
- **合并材质**：能用同一套 `Material` 的尽量共用；纹理尽量 **图集（atlas）**，避免「一物体一材质一贴图」导致状态切换频繁。

你们当前是 **每格 tile 独立 mesh + 建筑再挂子物体**，天然 draw call 偏多，这是和 `renderBufferDirect` 最吻合的优化点。

### B. 阴影（你项目里很重）

`environment.js` 里方向光 **2048×2048 阴影 + `PCFSoftShadowMap`**，阴影 pass 会再跑场景，CPU/GPU 都贵。

- 适当 **降低 `shadow.mapSize`**（例如 1024），看画质是否可接受。
- 只对 **真正需要投影的物体** `castShadow`，地面/大平面可只 `receiveShadow`。
- 收紧 **阴影相机视锥**（`shadow.camera` 的 left/right/top/bottom），减少进阴影贴图的对象。
- 若仍吃紧，可尝试换 **`BasicShadowMap`**（更糊但更快）或关掉软阴影类型。

### C. 渲染器与分辨率

```17:30:/home/zuoyang/workspace/CubeCity/src/js/renderer.js
    this.instance = new THREE.WebGLRenderer({
      canvas: this.canvas,
      antialias: true,
      ...
    })
```

- **`pixelRatio`**：高 DPR 下像素量暴涨；可 cap 到 `Math.min(devicePixelRatio, 1.5~2)`。
- **`antialias: true`**：有多一层 MSAA 成本；可对比关掉或用后期抗锯齿（需改管线，工作量更大）。

### D. 场景与更新

- **Frustum culling**：Three 默认会做；若物体特别多，可用 **LOD**（远处低模或 billboard）减少进 `renderObject` 的三角形。
- **透明物体**：尽量控制顺序和数量；透明多会多 pass、排序开销大。
- **调试辅助**：例如 `HemisphereLightHelper` 若 `visible: true` 会一直画，发布或性能测试时应关掉。

---

## 3. 建议你怎么验证「改对了」

1. 打开 **Rendering** 里 **「Show FPS」** 或看 Performance 长帧是否缩短。
2. 用 **Spector.js** 或 Three 的 `renderer.info` 看 **calls / triangles**（改前后对比）。
3. 优先做 **合批/实例化 + 阴影减负**，通常对 `renderBufferDirect` 时间最直接。
